# 문서 구조와 스키마

작업별로 필요한 절만 읽는다. 최초 적용은 저장 범위와 폴더 역할, 새 문서는 정체성, 출처·주장·처리 장부를 다룰 때는 관리 기록의 역할을 확인한다.

## 저장 범위와 적용

- 해당 프로젝트 루트의 `docs/`에 저장한다. 프로젝트와 무관한 임시 채팅 폴더를 루트로 추정하지 않는다. 맥락과 기존 파일로 루트를 확인할 수 없을 때만 위치를 질문한다.
- 계획·요구사항·설계·결정·작업일지·진행 상황을 기본 기록한다. 프로젝트상 필요한 문서와 사용자가 저장을 요청한 문서도 기록한다.
- 문서 종류별 폴더와 문서의 역할을 명확히 하고 중복을 지속적으로 통합한다. 대체된 결정은 `docs/legacy/`에 이유와 후속 문서 연결을 남겨 보존한다.
- 사용자 지시가 기본 구조보다 우선한다. 기존 프로젝트 규칙을 확인하고 새 작업부터 점진적으로 적용한다. 파일명·폴더 구조가 다르다는 이유로 기존 자료를 일괄 이전하지 않는다.
- 유지 관리는 프로젝트를 작업하는 동안 수행한다. 스킬 사용 자체는 예약 작업, 추가 도구 설치, 외부 업로드, 커밋, 루트 `AGENTS.md` 수정, 다른 프로젝트 변경을 허용하지 않는다.

**한 목적에 대표 문서 한 곳.** 현재 지식은 대표 문서에서 갱신하고 다른 문서는 링크로 연결한다. 문서 ID는 이동해도 유지한다. 분류·태그·그래프를 만들기 위해 같은 내용을 복제하지 않는다.

**문서량보다 재사용 가치.** 의미 있는 작업 단위에서 저장한다. 빈 폴더, 주제 없는 개체 문서, 매 명령의 기록, 조회만을 위한 로그를 만들지 않는다.

## 층과 소유권

`docs/` 안에서 원자료, 유지 관리 지식, 프로젝트 실행 기록, 레거시, 파생 상태를 구분한다. 파생 색인·검색·그래프를 사실의 근거로 사용하지 않는다. 다른 프로젝트의 문서를 합쳐 공통 루트에 저장하지 않는다.

| 경로 | 역할과 경계 |
| --- | --- |
| `index.md` | 문서 ID·링크·한 줄 목적·생애 상태의 진입점. 상세 내용은 연결한다. |
| `schema.md` | 실제 폴더별 역할, 명명, 스키마 버전, 링크·근거·유지 관리 규칙과 예외. |
| `overview.md` | 프로젝트 목적·범위·지식 구조의 짧은 종합. 일정·현재 진척은 상태 문서로 연결한다. |
| `log.md` | 문서 생성·갱신·통합·교체·이동·점검의 추가 기록. 작업일지와 상세 내용을 복제하지 않는다. |
| `plans/` | 목표·단계·예정 행동·의존성·완료 기준. 현재 진척은 연결한다. |
| `requirements/` | 요구사항·제약·수용 기준. 구현 방식과 선택 이유는 다른 종류로 연결한다. |
| `design/` | 구조·인터페이스·데이터·동작과 적용 범위. 결정의 이유는 연결한다. |
| `decisions/` | 선택·대안·이유·영향·확정 권한·적용 시점. 제안과 확정 결정을 구분한다. |
| `journal/` | 날짜별 실제 작업·확인 결과·실패·학습·그때의 판단. 이력이다. |
| `status/` | 현재 완료·진행·차단·미검증·다음 행동의 대표 위치. 상세 이력은 연결한다. |
| `research/` | 조사·비교·종합 분석. 원자료 요약과 구분한다. |
| `sources/` | 긴 원자료를 재사용할 때 필요한 요약과 출처 연결. 모든 짧은 입력에 별도 요약을 만들지 않는다. |
| `knowledge/` | 여러 작업에서 재사용되는 개념·교훈·용어·문제 해결·절차. 설계·요구사항의 복제본을 만들지 않는다. |
| `raw/` | 보존이 필요한 입력의 불변 버전. 문서·대화 발췌·검증 결과를 출처 종류별로 분류한다. |
| `legacy/` | 대체·통합·종료된 기록. 현행 근거와 기본 검색에서 구분한다. |
| `.wiki/` | 원자료 장부, 주장 장부, 처리 상태, 필요한 변경 복구 자료. 사람용 문서의 복제 저장소가 아니다. |

기본 관리 파일은 필요한 시점에 만들고, 종류별 폴더는 실제 내용이 생길 때 만든다. 운영 가이드·테스트 전략·데이터 명세처럼 다른 역할이 필요하면 `schema.md`에 정의한 뒤 추가한다. 폴더를 추가하기 전에 기존 역할에 포함되는지 확인한다. 분류 기준은 폴더 한 축으로, 교차 주제는 태그와 연결로 표현한다.

`knowledge/`에서도 문서가 한 개뿐인 하위 종류를 과도하게 나누지 않는다. 기존 `lessons/`나 `troubleshooting/`는 필요에 따라 유지하거나 통합하고 연결을 복구한다. 단어가 다르다는 이유만으로 이름을 바꾸지 않는다.

## 문서의 정체성

새 유지 관리 문서는 UTF-8 Markdown을 기본으로 하고 사용자 요청 형식을 보존한다. 제목과 본문은 프로젝트의 언어를 따른다. 파일명은 기존 규칙이 없으면 의미 있는 kebab-case다. 날짜별 작업일지는 `YYYY-MM-DD.md`, 결정은 기존 번호 규칙을 재사용한다.

각 실질 문서에 변경하지 않는 `id`를 부여한다. ID는 프로젝트 안에서 유일하고 경로와 분리한다. 통합 시 대표 ID는 유지하고 통합된 ID를 `merged_into`로 연결한다. 과거 문서의 불변 스냅샷은 별도 ID와 `snapshot_of`를 사용한다.

최소 머리말:

```yaml
---
id: doc-auth-design
type: design
summary: 인증 구조와 인터페이스
lifecycle: active
created: 2026-10-13
updated: 2026-10-13
---
```

생애 상태는 `draft`, `active`, `superseded`, `merged`, `archived`다. 최신성은 별도로 계산한다. 기존 `status: current/stale`는 이전 표기임을 구분하고 실제 검토 후 이 스키마로 옮긴다. 상태 문서의 작업 상태는 `planned`, `in-progress`, `blocked`, `awaiting-validation`, `done`으로 본문에 기록하며 생애 상태와 혼용하지 않는다.

다음 필드는 필요할 때 추가한다. 자동 점검용 목록은 한 줄 JSON 형식으로 쓴다. 일반 YAML과 호환되며 추가 YAML 라이브러리를 요구하지 않는다.

```yaml
aliases: ["로그인 구조"]
sources: ["src-auth-doc-v1"]
claims: ["claim-token-expiry"]
relations: [{"type":"depends_on","target":"doc-auth-requirements","basis":"EXTRACTED"}]
```

관계는 `depends_on`, `implements`, `supports`, `contradicts`, `supersedes`, `derived_from`, `related_to`처럼 의미를 표시하고 실제 문서 ID를 대상으로 한다. 직접 명시된 관계와 추론한 관계를 구분한다. 추론한 관계만으로 영향이나 승인 결과를 확정하지 않는다. 모든 개체·명사에 문서를 만들지 않는다.

본문 링크는 파일 기준 상대 Markdown 경로를 기본으로 한다. Obsidian 위키 링크는 요청되거나 기존 환경에서 필요할 때 명확한 경로로 추가한다. 같은 이름의 문서가 여러 개면 대상으로 추측하지 않는다. 문서 ID 연결은 의미를, 경로 링크는 실제 탐색을 담당한다.

## 관리 기록의 역할

서로 다른 세 가지 기록을 하나의 신뢰 장부로 합치지 않는다. 실제 기록이 생길 때만 생성한다.

- `.wiki/sources.json`: 출처 ID, 원본 위치, 보존 버전·해시, 수집일·게시일, 독립성 그룹, 검토 상태, 재확인 시점. 해시는 내용 정체성이지 사실의 진실성을 뜻하지 않는다.
- `.wiki/claims.json`: 중요한 사실·수치·충돌·판단의 ID와 문서 위치, 근거, 추출·계산·추론 구분, 검토 결과. 모든 평범한 문장을 등록하지 않는다.
- `.wiki/state.json`: 어떤 출처 버전을 어떤 문서에 반영했는지와 작업 상태. 확인된 결과를 반영한 뒤에만 처리 해시를 갱신한다.

자료 장부 형식 예시:

```json
{"schema":"project-docs-wiki.sources.v1","sources":[{"id":"src-auth-doc-v1","raw_path":"raw/documents/auth-v1.md","sha256":"실제로 계산한 SHA-256","live_path":"src/auth/config.ts","authority":"primary","independence_group":"auth-config","state":"active","refresh_due":null}]}
```

`raw_path`는 `docs/` 기준, 선택적인 `live_path`는 프로젝트 루트 기준 상대 경로다. 원자료 복사본과 현재 파일이 같은 내용을 나타낼 때만 두 경로를 대응시킨다. 서로 다른 형식의 변환 결과를 같은 해시로 비교하지 않는다. 외부 URL은 `locator`에 기록하고 로컬 보존본만으로 원격 최신성을 주장하지 않는다.

주장 장부는 `schema: project-docs-wiki.claims.v1`, `claims` 목록을 사용한다. 항목은 `id`, `page_id`, `location`, `statement`, `basis`, `assessment`, `source_ids`, `verified_at`, `verification`을 담는다. 목록의 의미와 검토 기준은 [근거와 유지 관리](evidence-maintenance.md)에 따른다.

처리 상태는 `schema: project-docs-wiki.state.v1`, `processed` 목록이다. 항목은 `source_id`, `page_id`, `sha256`을 담는다. 원자료를 읽었다는 이유로 완료를 기록하지 않는다. 입력 버전이 바뀌면 영향을 받는 현행 문서부터 갱신한다.

색인·요약·그래프는 실제 문서에서 파생된다. 하나를 수정해 원본 기록을 대신하지 않는다. 큰 프로젝트는 종류·주제별 색인을 두고 상위 색인은 하위 색인으로 안내한다. 그래프·검색 엔진은 필요할 때만 도입하며 없어도 Markdown과 일반 검색으로 운영한다.
