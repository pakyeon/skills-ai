# 프로젝트 운영 절차

요청에 해당하는 절만 실행한다. 조회·재개에는 해당 절을, 쓰기에는 저장 공통과 완료 기준 및 실제 작업 절을 읽는다. 일괄 변경과 복구는 이동·통합·여러 문서의 연쇄 수정 때 적용한다.

## 저장 공통과 완료 기준

**변경은 추적 가능하게.** 문서·연결·근거·색인을 함께 갱신하고 작업 ID와 이유를 남긴다. 통합·이동은 원본 복구와 연결 복구를 준비한 뒤 실행한다.

관련 대표 문서, 현재 진행 상황, 작업일지, 색인·연결, 필요한 근거 기록이 실제 변경과 일치해야 한다. 대체된 결정과 통합 전 고유한 정보가 보존되고 깨진 연결이 없어야 한다. 미검증 작업은 미검증 상태로 남긴다.

저장·수정한 문서 링크, 핵심 변화, 통합·레거시 이동과 미해결 항목을 짧게 보고한다. 완료·원자 적용·전체 검증은 실제로 수행한 범위에 한해서만 주장한다.

## 재개와 초기 적용

프로젝트 루트를 확인하고 기존 지침·`docs/schema.md`·`docs/index.md`·현재 상태 문서를 읽는다. 색인을 실제 파일과 대조한 뒤 관련 문서와 그 근거로 좁힌다. 필요한 연결·근거가 부족하면 원자료·현재 코드·실제 검증 결과를 확인한다. 인덱스와 전문 검색을 모두 확인하기 전에는 관련 문서가 없다고 단정하지 않는다.

처음 적용하는 프로젝트는 기존 파일과 역할을 조사하고 필요한 진입점·프로젝트별 스키마·현재 상태부터 작성한다. 사용자가 제공한 정보만 기록하고 빈 업무 문서 전체를 미리 만들지 않는다. 기존 문서는 실질적으로 수정할 때 ID·역할·연결을 보완한다.

초기 이전에서는 기존 기록을 보존하고 역할이 확실한 부분부터 옮긴다. 출처 없는 과거 주장에 새 근거를 꾸며 붙이거나 과거 날짜를 추정하지 않는다.

## 자료·작업 결과 반영: 두 단계

**작성 전에 통합 계획.** 새 정보와 기존 문서를 비교한 뒤 신규·갱신·충돌·무변경으로 분류한다. 여러 출처가 같은 주제를 다루면 대표 문서로 합친다.

### 1. 읽고 분석하기

새 자료와 의미 있는 작업 결과의 범위, 출처, 보존 필요성을 확인한다. 프로젝트 방향에 필요한 정보만 추린다. 필요한 원자료는 출처 종류별 `raw/`에 버전으로 보존한다. 대화 요약은 요약임을, 발췌는 발췌임을 밝히고 원문 전체처럼 취급하지 않는다.

입력 해시·게시 시점·수집 시점·근거 위치와 기존 문서의 ID·별칭·관련 내용을 확인한다. 변경되지 않은 입력과 이미 반영된 지식을 재사용하되 기존 결과의 연결과 현재 적용 범위도 점검한다.

각 정보의 처리를 신규, 갱신, 충돌, 무변경으로 분류한다. 여러 자료를 함께 받으면 주요 개념과 중복을 먼저 비교해 대표 문서와 영향을 받는 문서를 정한다. 분석이 실패한 내용을 현행 문서에 반영하지 않는다. 처리 가능한 자료만 범위를 밝혀 진행한다.

### 2. 연결된 문서로 반영하기

대표 문서를 갱신하고 새 역할에만 새 문서를 만든다. 중요한 주장과 출처·추론·검증 범위를 표시한다. 충돌은 [근거와 유지 관리](evidence-maintenance.md)에 따라 처리한다.

요구사항·설계·결정·검증·현재 상태의 영향을 확인하고 관련 문서로 연결한다. 자료가 바뀌었어도 레거시 문서의 당시 본문을 연쇄 수정하지 않는다. 새로운 근거가 추가되었다는 사실과 과거 판단이 바뀌었다는 사실을 구분한다.

문서 내용, 근거 장부, 처리 상태, 색인·관련 링크, 문서 변경 로그를 같은 논리적 작업 범위에서 갱신한다. 원자료 버전은 덮어쓰지 않는다. 정보가 추가되지 않으면 새 지식 페이지를 만들지 않는다. 명시적인 수집·정리 작업에서는 검토했으나 반영하지 않은 이유를 짧게 남긴다.

## 프로젝트 실행과 기록

- 계획에는 목표·단계·완료 기준을, 요구사항에는 수용 기준을, 설계에는 실행 방식을, 결정에는 이유와 확정 주체를 기록한다. 필요할 때 ID로 연결하며 문서 수·파일명 일치를 강제하지 않는다.
- 현재 상태의 대표 위치는 `status/`에서 정한다. 작업일지는 실제 수행과 학습의 날짜별 이력이다. 현재 상태를 작업일지에서 반복 복제하지 않는다.
- 구현이 끝났지만 확인이 남았으면 `awaiting-validation`으로 기록한다. 실제 테스트·관찰·검토와 적용 범위가 완료 조건을 충족했을 때 완료로 표시한다.
- 사용자의 의도나 프로젝트에 영향을 주는 제안은 제안 상태로 둔다. 이미 허용된 구현 선택은 실제 결정 주체와 이유를 기록한다. AI의 제안을 사용자 승인으로 둔갑시키지 않는다.
- 실질 작업 단위 종료 시 질문·변경·확인·결정·교훈·남은 행동을 짧게 정리한다. 필요한 지식을 현행 문서에 통합하고 작업일지에서 연결한다. 매 발화·명령의 전문을 저장하지 않는다.

## 조회와 지식 재사용

관련 색인 → 현행 대표 문서 → 중요한 주장과 근거 → 의존·대체 관계 순서로 좁힌다. 최신성 징후와 실제 범위를 확인하고 확인된 내용·추론·미해결 충돌을 구분해 답한다.

기본 조회는 읽기만 한다. 조회에서 얻은 재사용 가치가 있는 분석은 저장 요청 또는 프로젝트 필요에 따라 적합한 기존 문서에 반영한다. 외부 조사 결과와 위키 내부의 기존 근거를 구분한다.

과거 결정을 묻거나 변경 이유를 검토하면 레거시를 읽고 당시 상태임을 표시한다. 현행 사실과 과거 사실이 같은 답변에서 섞이지 않도록 시점을 명시한다.

## 일괄 변경과 복구

통합·이동·여러 문서의 연쇄 수정은 적용 전에 대상 경로·문서 ID·변경 전 해시·이동 대응·근거·영향 링크를 정리한다. 실제 수행할 수 있는 작업 묶음으로 나눈다. 이미 허용된 문서 정리를 위해 승인 질문을 반복하지 않는다.

변경 전 내용을 복구할 수 있도록 Git 이력 또는 `.wiki/operations/<작업 ID>/`의 원본·작업 기록을 준비한다. 저장소가 있다는 이유만으로 작업 전 내용이 커밋됐다고 가정하지 않는다. 기록에 민감한 내용을 추가 복제하지 않는다.

적용 직전에 대상이 바뀌었으면 다시 읽고 변경안을 계산한다. 다른 작성자의 변경을 덮어쓰지 않는다. 공유 문서에 대한 실제 병렬 작성이 있으면 쓰기 담당을 하나로 조정한다. 추가 에이전트를 자동 생성하지 않는다.

지원하는 도구에서는 임시 파일과 원자 교체를 사용한다. 여러 파일에 대한 원자 적용을 지원하지 않으면 진행 상태를 남기고 단계별로 검증한다. 단순 파일 복사에 원자 트랜잭션을 구현했다고 주장하지 않는다.

실패하면 영향 범위를 확인하고 이번 작업이 쓴 버전임을 확인한 대상만 복구한다. 이후의 사용자 변경을 롤백하지 않는다. 입력·출력·색인·링크가 일치한 뒤에만 처리 완료와 해시를 기록한다. 같은 실패가 반복되면 원인을 재검토하고 미완료 범위를 알린다.

## 완료와 종료

변경 문서·현행 상태·이력·근거 연결·파생 색인을 확인한다. 종료된 계획은 필요할 때 보존하지만 완료됐다는 이유로 유효한 요구사항·설계·결정을 레거시로 보내지 않는다. 미해결 검증·충돌·자료 누락은 현재 상태와 관련 문서에 남긴다.
